# 我的网站是怎么搭起来的

写这篇文章，是想把网站的整体框架和各个功能梳理一遍。一方面是给自己留个备忘，另一方面，如果有朋友看到这个网站想了解它是怎么跑起来的，也能省去反复解释。下面按“文件结构”“功能”“提速机制”三条线来讲，前面偏日常使用，后面偏技术细节，看不懂的地方可以跳过，不影响你发文章。

## 整体是什么

网站用 Hugo 生成，托管在 GitHub Pages 上，地址是：

```
https://natural-system.github.io/Hugo-Minimalist-Text/
```

没有数据库，没有后台，所有页面在发布前一次性生成好。写文章就是新建 Markdown 文件，发布就是推送到 GitHub。分类、归档、搜索、评论、短链都是自动的。

## 写作和发布的工作流

我写文章用的是 Typora，发布用的是 GitHub 桌面客户端（GitHub Desktop）。这个组合是我用了几年之后固定下来的，原因很简单：写作和发布可以完全分开，写的时候只关心文字，发的时候只点几下鼠标，不需要碰命令行。

Typora 是一个所见即所得的 Markdown 编辑器。左边写，右边实时看到排版效果，不用记语法。它保存的就是纯文本 `.md` 文件，正好是 Hugo 需要的格式。我在 Typora 里新建文件，写好页头和正文，保存到 `content/posts/` 下，这一步就算写完了。

发布靠 GitHub Desktop。我把项目文件夹和 GitHub 仓库关联好。每次写完文章，或者改完网站代码，打开 GitHub Desktop，它会自动列出所有改动过的文件。我在左下角填一句简短的提交说明，点“Commit to main”，再点“Push origin”，就推送到 GitHub 了。推送之后，GitHub 上配置好的自动流程会检测到变化，自动安装 Hugo、构建网站、发布到 GitHub Pages。整个过程不需要我手动上传任何文件，也不需要敲命令。一两分钟后刷新线上页面，就能看到最新的内容。

这个流程最省心的地方在于，它**不区分改动大小**。我改了一个错别字、调了一个标点符号、换了一张配图、修了一行 CSS，和写了一整篇新文章，走的是完全相同的流程。GitHub Desktop 会精确识别出哪个文件、哪一行变了，只把变化的部分推上去。GitHub Actions 检测到推送，就重新构建一次。我不需要判断“这次改动够不够大、要不要发布”，只要推送，它就会部署。

也就是说，写作和发布之间没有“中间步骤”。Typora 保存即完成写作，GitHub Desktop 点两下即完成发布。改半个标点符号和写三千字长文，操作完全一样。这个特性让我可以随时修修补补，不用担心“小改动不值得发一次”的问题。

如果想本地预览效果，也可以在项目根目录打开终端执行 `hugo server`，浏览器打开 `http://localhost:1313/Hugo-Minimalist-Text/`，改文件保存后页面会自动刷新。看完按 `Ctrl+C` 停止。但这一步不是必须的，Typora 保存完直接推送到 GitHub Desktop 也可以，线上构建成功就能看到。

下面按文件夹逐个说。

## 根目录的几个文件

**`hugo.toml`** 是网站的全局配置。里面写了网站地址、标题、作者、描述，还定义了分类和标签的映射，以及文章的链接规则。文章的链接规则决定了每篇文章的地址长什么样。这个文件一般不动，动之前要清楚每行是干什么的。

**`.github/workflows/hugo.yml`** 是自动部署配置。每次我把代码推送到 GitHub，这个文件里的流程会自动跑起来：安装 Hugo、构建网站、把生成的页面发布到 GitHub Pages。我不需要手动上传任何东西，推送就是发布。这个文件是“改半个标点也能自动识别”的关键——它监听的是整个仓库的变化，任何文件变动都会触发一次新的构建。

## content 文件夹：所有内容

`content/` 放的是网站的所有文字内容。每个 `.md` 文件对应一个页面。

**`content/posts/`** 是所有文章的家。文件名我习惯用“年-月-日-标题”，比如 `2026-11-04-我第一次用短链接.md`。每篇文章开头有一段页头信息：

```yaml
---
layout: post
title: "我第一次用短链接"
date: 2026-11-04
categories: 软件
---
```

`layout` 告诉 Hugo 用文章模板渲染，`title` 是标题，`date` 决定排序和归档，`categories` 决定归到哪个分类。分类名必须和导航栏里的一字不差。

**`content/logs/`** 是日志页面。和文章不同，日志按年份分文件，比如 `2025.md`、`2026.md`。文件内容用标题层级区分年月日：

```markdown
# 2026

## 十月

### 2026-10-01

今天写了一条日志。
```

`#` 是年份，`##` 是月份，`###` 是具体日期。日志页会把这些按时间线倒序显示，侧边栏有年份和月份折叠导航。

**`content/about.md`、`archive.md`、`categories.md`、`community.md`、`log.md`、`_index.md`** 这几个是独立页面，分别对应导航栏里的“关于”“年份归档”“全部分类”“问答交流”“日志”和首页。它们本身内容不多，主要作用是告诉 Hugo“这个路径存在，请用对应的模板渲染”。

## layouts 文件夹：网站长什么样

`layouts/` 决定每个页面显示成什么样子。这是网站功能最集中的地方。

**`layouts/_default/baseof.html`** 是所有页面的“外壳”。导航栏、页脚、搜索框、主题切换、字号调节、返回顶部按钮、阅读进度条，全在这里。每个具体页面（首页、文章页、归档页）都套在这个外壳里，通过 `{{ block "main" . }}` 把各自的内容嵌进来。改导航栏分类链接、改页脚文字，都在这个文件里。

**`layouts/_default/single.html`** 是单篇文章的模板。标题、发布日期、分类、字数、预计阅读时间、正文、目录、评论区，都在这里。文章标题下方的短链展示框也是在这里加的：它读取文章路径，算出十位哈希，拼成短链显示出来，旁边带复制按钮。

**`layouts/index.html`** 是首页模板。它把所有文章导出成一个列表，用 JavaScript 做前端分页，每页二十篇，带页码、上一页下一页、跳转输入框。

**`layouts/archive.html`** 是年份归档页模板。按年份分组列出所有文章，每年超过十篇时折叠，点“展开”看全部。这里用的是纯 CSS 的复选框技巧，不需要 JavaScript。

**`layouts/categories.html`** 是分类总览页模板。列出所有分类，每个分类显示前五篇文章，超过五篇时给“查看全部”链接。

**`layouts/categories/list.html`** 是单个分类页的模板。比如点进“软件”分类，看到的就是这个模板渲染的页面，列出该分类下所有文章，带前端分页。

**`layouts/log.html`** 是日志总页模板。它把所有年份的日志内容汇总，按时间线倒序、分批加载显示，侧边栏有年份和月份折叠导航。这个页面用了无限滚动，滚到底部自动加载更多。

**`layouts/logs/single.html`** 是单个日志年份页的模板。和 `log.html` 不同，它只显示当前年份的日志，左侧有年份导航，右侧是正文。这个模板是后来加的轻量化版本，避免一次加载所有年份的日志。

**`layouts/partials/generate-shortlinks.html`** 是短链生成逻辑。它在构建时遍历所有文章，为每篇算出十位哈希短码，生成一个跳转页写到 `public/s/短码/` 下。如果两篇文章算出同一个短码，构建会直接失败并报错，不会出现线上 bug。这个文件由 `baseof.html` 用 `partialCached` 调用一次，不干扰任何页面的正常输出。

## 网站的几个功能，分别在哪里实现

### 短链接

短链由 `generate-shortlinks.html` 生成，展示在 `single.html` 里。每篇文章自动获得一个 `/s/十位字符/` 的跳转页，访问它会自动跳回原文。短链和长链并存，长链是真实地址，继续被搜索引擎收录，短链是额外入口。如果两篇文章短码冲突，构建会失败，给其中一篇加一行 `shortlink: "自定义码"` 就能解决。重要的、分享得多的文章，建议手动指定 `shortlink` 锁住，避免重命名文件导致短链失效。

### 四种主题模式

主题切换在 `baseof.html` 里实现。导航栏右侧有四个圆点，分别对应日光、羊皮纸、护眼绿、暗黑四种主题。点击切换时，JavaScript 把选中的主题写到页面的 `data-theme` 属性上，CSS 根据这个属性切换整套颜色变量。选择会存进浏览器的 localStorage，下次打开还是上次选的。

### 正文字号调节

同样在 `baseof.html` 里。导航栏右侧有“小、中、大”三个字，点击后 JavaScript 把字号写到 `data-font-size` 属性上，CSS 根据这个属性调整正文段落、列表、表格、引用的字号。选择也会记住。

### 字数统计和阅读时间

文章页的字数和阅读时间在 `single.html` 里算。用 Hugo 的 `findRE` 统计正文里真实字符数，再除以五百估算阅读分钟数。日志页的字数在 `log.html` 里用 JavaScript 算，区分中文字符和英文单词，加总后除以四百估算阅读时间。

全站总字数在 `baseof.html` 的页脚里算。遍历所有文章，统计字符数加总，超过一万时显示成“几万字”。

### 目录（TOC）

文章页右侧的目录在 `single.html` 里用 JavaScript 生成。它扫描正文里所有二级、三级、四级标题，找出实际出现的最高等级，把标题按相对层级映射成实心圆、空心圆、短横线三种符号，点击跳转到对应位置。如果没有标题，显示“暂无目录”。

### 搜索

搜索框在 `baseof.html` 的导航栏里。所有文章的标题、链接、日期、正文在构建时导出成一个 JavaScript 数组，输入关键词时在前端匹配标题和正文，弹出结果窗口，显示匹配文章和出现次数。搜索数据库随首页一起生成，文章多了以后首页体积会变大，但功能正常。

### 评论

文章页和日志页底部都有 Giscus 评论框，基于 GitHub Discussions。读者需要登录 GitHub 才能评论。文章页的评论按标题关联，日志页的评论按路径关联。改文章标题会导致旧评论和新标题对不上，所以重要文章的标题尽量别改。

### 分页

首页和分类页用前端分页。所有文章导出成数组，JavaScript 按每页二十篇（首页）或三十篇（分类页）切分，生成页码、上一页下一页、跳转输入框。翻页时只改 URL 的查询参数，不刷新页面。

### 年份归档折叠

归档页每年超过十篇时折叠，点“展开”看全部。这里用的是纯 CSS 的复选框技巧：一个隐藏的复选框控制后面列表的显示隐藏，两个标签分别做“展开”和“收起”按钮。不需要 JavaScript。

### 阅读进度条和返回顶部

进度条在 `baseof.html` 顶部，随滚动位置变长。返回顶部按钮在右下角，滚动超过一定距离后出现，点击平滑回到顶部。两者都是原生 JavaScript 实现。

## 网站提速机制（技术细节，可跳过）

这部分偏技术，看不懂不影响日常使用，但如果你好奇“为什么日志文件那么大、页面打开却不卡”，可以看这里。

整体思路是：**不让浏览器在首屏渲染全部内容，而是按需加载、分批渲染、前端切片**。具体分布在几个文件里。

### 日志总页：分批渲染 + 无限滚动

**`layouts/log.html`** 是所有日志的总入口。它把所有年份的日志内容一次性读进页面，但**不直接渲染**，而是藏在一个 `display: none` 的容器 `#raw-log-content` 里，作为“原始数据池”。首屏只渲染空容器 `#rendered-log-wrapper`。

页面加载后，JavaScript 扫描原始数据，按年份、月份、日期重新组织成数组，然后每次只取 **50 条**（`BATCH_SIZE = 50`）渲染到页面上。用 `IntersectionObserver` 监听底部的触发点，用户滚到接近底部时自动加载下一批。

这样一来，即使日志文件有三五兆，首屏 DOM 里也只有几十条，浏览器解析和布局的开销小得多。侧边栏时间线导航也基于同一份数据构建，点某个日期时，如果还没渲染到那一条，会先自动加载几批直到它出现，再滚动定位。

字数统计是在原始数据上算的，算的是全部日志的总字数，不受分批加载影响，所以用户看到的字数和阅读时间是准确的。

### 日志年份单页：按年拆分 + 静态渲染

**`layouts/logs/single.html`** 是轻量化版本。它不汇总所有年份，而是每个年份一个页面，Hugo 构建时直接静态输出 `.Content`，不经过 JavaScript 重组，也没有无限滚动。一个年份的日志量有限，体积天然就小，打开快，不拖累其他年份。

这两个模板对应两种使用场景：想看全部时间线、体验“滚到底自动加载”，走 `log.html`；想快速打开某一年、只加载那一年，走 `logs/single.html`。

### 首页和分类页：前端分页

**`layouts/index.html`** 和 **`layouts/categories/list.html`** 把所有文章的标题、链接、日期导出成 JavaScript 数组，页面只渲染当前页的 20 篇（首页）或 30 篇（分类页）。翻页时用 `history.pushState` 改 URL 参数，重新切片渲染，不刷新页面。DOM 里始终只有当前页的几十个条目，文章几百篇也不卡。

### 归档页：CSS 折叠

**`layouts/archive.html`** 每年超过 10 篇时用纯 CSS 复选框折叠，默认只显示前 10 篇，点“展开”看全部。这不是动态加载，HTML 全都在、只是 CSS 隐藏。好处是不需要 JavaScript，坏处是 DOM 里其实包含所有文章。几百篇规模没问题，如果到几千篇，这个页面会比日志页重。

### 目录：运行时生成

**`layouts/_default/single.html`** 的目录不是构建时生成的，而是页面加载后 JavaScript 扫描正文的 `h2, h3, h4` 动态创建。这样 HTML 里不用预存一份目录结构，目录只存在于渲染后的 DOM 里。

### 搜索：构建时导出 + 前端匹配

**`layouts/_default/baseof.html`** 的搜索是所有文章在构建时被 `plainify | jsonify` 塞进一个数组，用户输入时在前端用正则匹配。不需要网络请求，搜索零延迟。代价是首页体积随文章数增长，收益是搜索体验即时。

### 短链生成：构建时一次性执行

**`layouts/partials/generate-shortlinks.html`** 用 `partialCached` 调用，整个构建只执行一次，遍历所有文章生成跳转页。不会因为页面多而重复计算，构建时间可控。

### 一张表总结

| 位置                                 | 技术                       | 效果                             |
| ------------------------------------ | -------------------------- | -------------------------------- |
| `log.html`                           | 分批渲染 + 无限滚动        | 首屏只渲染 50 条，滚动时按需补   |
| `logs/single.html`                   | 按年份拆分 + 静态渲染      | 只加载当前年份，不拖累其他年份   |
| `index.html`、`categories/list.html` | 前端分页                   | 首屏只渲染当前页 20/30 篇        |
| `archive.html`                       | CSS 折叠                   | 默认只显示前 10 篇（DOM 仍全量） |
| `single.html` TOC                    | 运行时生成                 | 不在 HTML 里预存目录结构         |
| `baseof.html` 搜索                   | 构建时导出 + 前端匹配      | 搜索零网络请求，代价是首页体积   |
| `generate-shortlinks.html`           | `partialCached` 一次性执行 | 构建不重复计算，时间可控         |

## 发布流程

每次发布，打开 GitHub Desktop，它会自动列出所有改动的文件。在左下角填一句简短的提交说明，点“Commit to main”，再点“Push origin”，就推送了。GitHub Actions 会自动构建并上线，一两分钟后生效。

如果想本地预览，可以在项目根目录打开终端执行 `hugo server`，浏览器打开 `http://localhost:1313/Hugo-Minimalist-Text/`，改文件保存后页面会自动刷新。看完按 `Ctrl+C` 停止。这一步不是必须的，直接推送到 GitHub Desktop 也可以。

推送后如果 Actions 显示红色叉，说明构建失败，最常见的原因是短链冲突、页头格式错误、或者 Markdown 里内嵌的 HTML 标签没闭合。点进失败记录看 `ERROR` 那一行，通常能直接定位。

有几件事我给自己定下规矩：不手动删 `public/` 里的文件，不改 `hugo.toml` 里的 `baseURL`，不重命名已经分享过短链的文章文件，不改文章标题。这四条踩过坑，记下来提醒自己。

## 最后

这套结构用了几年，不复杂，但细节不少。总结成一句话：写作在 Typora，发布用 GitHub Desktop，内容放 `content/`，外观和功能在 `layouts/`，配置在 `hugo.toml`。短链、分类、归档、搜索、评论、主题、字号、字数统计都是自动的，日常只需要写文章，然后在 GitHub Desktop 里点两下推送。

遇到不确定的改动，先提交一次备份，再动手。
